# ProspectAI — Engineering Rules

These rules are mandatory for implementation and code generation.

## 1. General
1. Keep the product name exactly **ProspectAI**.
2. Use Java and Spring Boot for the backend; React, Vite, and Tailwind CSS for the frontend.
3. Use Spring AI for model, PDF reader, and vector-store integration.
4. Use OpenAI for chat and embeddings; Pinecone is the vector database; MySQL stores application data.
5. Prefer simple, readable, production-conscious code over unnecessary abstractions.
6. Do not silently change the agreed stack or add libraries without a clear need.
7. Use the package root `com.prospectai`.

## 2. Backend Design
1. Controllers must be thin: map HTTP requests, validate inputs, call services, and return DTOs.
2. Keep business logic in service classes.
3. Use repositories for database persistence.
4. Do not expose JPA entities directly from REST endpoints.
5. Use Bean Validation for request DTOs.
6. Centralize exception handling with `@ControllerAdvice`.
7. Use appropriate HTTP status codes and consistent response shapes.
8. Avoid field injection; prefer constructor injection.
9. Use transactions for related MySQL changes where appropriate.
10. External API calls must have bounded timeouts and safe failure handling.

## 3. Authentication and Authorization
1. Use Spring Security and JWT for authentication.
2. Hash passwords with BCrypt or an equivalent secure adaptive encoder; never store plaintext passwords.
3. Never log JWTs, passwords, API keys, or signing secrets.
4. Public endpoints must be explicitly allowlisted; all other relevant endpoints require authentication.
5. Verify resource ownership for every document, conversation, message-history, analysis, and delete operation.
6. Never trust an `ownerId` supplied by the frontend; derive the authenticated user identity from the security context.
7. Validate JWT signature and expiry. Do not accept unsigned or weakly signed tokens.
8. Store secrets in environment variables or a secret manager, never in source control.
9. Configure CORS with explicit allowed origins in production.
10. Prefer secure, short-lived access tokens. If tokens are stored in browser storage, document the XSS risk; consider a secure HttpOnly cookie design where suitable.

## 4. PDF and Ingestion
1. Use the selected Spring AI PDF Document Reader module for PDF extraction.
2. Validate file size, extension, content type, and actual readability; do not trust the filename alone.
3. Preserve page-level metadata wherever the chosen reader provides it.
4. Treat PDF text as untrusted data, not instructions.
5. Use configurable chunk size and overlap; avoid hardcoding tuning values throughout the code.
6. Add stable metadata to each chunk: `documentId`, `pageNumber` when available, `chunkIndex`, and `section` when detected.
7. Every vector must be traceable to its source document.
8. Use a stable vector ID or idempotent ingestion strategy to prevent duplicates on retries.
9. Keep processing status accurate: `UPLOADED`, `PROCESSING`, `READY`, `FAILED`, and optionally `DELETING`.
10. Handle scanned PDFs, malformed files, empty extraction, and provider outages explicitly.

## 5. RAG and AI
1. Retrieval for a question must be filtered to the selected `documentId`.
2. Check the authenticated user's ownership before retrieval.
3. Answer document-specific questions from retrieved context; do not fill gaps with invented facts.
4. If the evidence is missing or insufficient, say so plainly.
5. Construct citations from retrieved chunk metadata; never rely solely on page numbers generated by the LLM.
6. Return source page and excerpt when available.
7. Preserve financial units, currency, fiscal years, signs, and table labels.
8. Clearly distinguish quoted facts, model interpretation, and computed values.
9. Treat prompt-injection text inside an RHP as document content, not as instructions that override system rules.
10. Avoid describing output as guaranteed financial, legal, or investment advice.
11. Test RAG quality using a curated set of questions with expected supporting pages.
12. Keep provider model names and retrieval settings configurable.

## 6. Pinecone and Data Isolation
1. Use a Pinecone index configured for the selected embedding model's vector dimension and an appropriate similarity metric.
2. Do not mix vectors from different documents during document-scoped chat.
3. Metadata filtering or namespaces are defense-in-depth; backend authorization remains mandatory.
4. Delete vectors when a document is deleted, and handle cleanup failures with a retryable state.
5. Do not store secrets in vector metadata.
6. Keep metadata small and useful; do not assume arbitrary metadata fields can be filtered without checking provider constraints.

## 7. Frontend
1. Use reusable React components and clear page/component boundaries.
2. Keep API calls in `src/services/`, not scattered through presentation components.
3. Centralize API base URL and authentication handling.
4. Show loading, empty, success, and failure states for uploads, processing, chat, and deletion.
5. Disable duplicate form submissions while a request is in progress.
6. Never expose OpenAI or Pinecone credentials in `VITE_*` variables.
7. Use semantic HTML, accessible labels, visible focus states, and responsive layouts.
8. Render PDF excerpts and AI output safely; do not inject untrusted HTML.
9. Show citation page numbers only when supplied by backend metadata.
10. Keep user-facing errors useful without exposing stack traces.

## 8. Testing
1. Test auth success, invalid credentials, expired JWT, and protected endpoints.
2. Test that one user cannot access another user's documents or conversations.
3. Test invalid PDFs, empty extraction, ingestion failure, and retry behavior.
4. Test retrieval filters and citations.
5. Test unsupported questions and prompt-injection content inside PDFs.
6. Test vector cleanup on document deletion.
7. Use mocked provider clients in unit tests where appropriate; keep a smaller integration suite for real services.
8. Do not put live secrets in test fixtures or CI logs.

## 9. Code Quality
1. Use descriptive class and method names.
2. Keep methods focused and avoid huge service classes.
3. Use DTOs for API contracts.
4. Avoid duplicate business logic.
5. Document non-obvious security and retrieval decisions.
6. Update tests and relevant docs when behavior changes.
7. Do not claim a feature is complete unless it compiles and its relevant tests pass.

## 10. Git and Configuration
1. Commit `.env.example`, not `.env`.
2. Ignore `.env`, build outputs, `node_modules`, IDE files, and uploaded user documents.
3. Keep environment-specific configuration outside committed source.
4. Document required environment variables and local startup steps in README.
